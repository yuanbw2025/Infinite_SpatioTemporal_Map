# 总体架构

## 1. 选择：模块化单体

项目采用一个领域内核、一个公众应用和一条数据管线。功能可以模块化，但不能各自建立数据模型、状态体系或基础设施。

```text
数据来源
  ↓
pipeline（导入、规范化、提取、审核、校验）
  ↓ 只能输出 contracts
packages/contracts（稳定数据边界）
  ↓
packages/core（领域规则、用例端口、模块注册）
  ↓
apps/web（书库、阅读器、地图、文博等功能模块）
```

## 2. 固定依赖方向

1. `contracts` 不依赖任何业务包。
2. `core` 只依赖 `contracts`。
3. `web` 依赖 `core` 和 `contracts`。
4. 功能模块之间不得直接导入内部实现，只能通过内核端口和稳定 ID 协作。
5. 数据管线不得为某个页面生成私有格式。

## 3. 扩展方式

新增功能时必须完成：

1. 确认现有领域模型能否表达需求；
2. 如需扩展，先修改契约并提供迁移；
3. 在内核添加用例或端口；
4. 以 `FeatureModule` 注册路由、导航和依赖；
5. 使用统一仓储获取数据；
6. 加入契约测试、核心规则测试和应用构建验证。

不得为新功能新建另一套实体 ID、全文索引、事件总线或全局状态。

## 4. 数据与展示分离

工作台和数据管线可以使用数据库；公众应用通过相同契约读取 API 或静态发布包。更换存储方式不改变领域模型和页面用例。

# 总体架构

## 核心决定

项目采用“模块化单体 + 六边形边界”：所有功能共享一个领域语言和应用服务，界面、静态数据包、数据库、API 与数据加工工具只是可替换适配器。项目规模增大时先拆模块，不拆语义；只有出现明确的独立部署压力时才考虑服务化。

```text
来源文本 / 影印页 / GIS / 文博目录
                  │
                  ▼
 pipeline：导入 → 分段 → 转换 → 提取 → 审核 → 发布
                  │ 只输出版本化 KnowledgePublication
                  ▼
 packages/contracts ───────── 唯一数据语言
                  ▲
 packages/core：领域规则 + 仓储端口 + 应用服务 + 功能内核
                  ▲
 packages/adapters：静态包 / 将来的数据库或 API 适配器
                  ▲
 apps/web：书库、阅读器、地图、人物、文博、检索
```

## 依赖方向

1. `contracts` 不依赖任何业务包。
2. `core` 只依赖 `contracts`，不知道 Vue、数据库或文件格式。
3. `adapters` 实现 `core` 端口，可以读取静态发布包、数据库或远程 API。
4. `web` 只通过 `ApplicationServices` 发起用例，功能页面不直接读取 JSON。
5. `pipeline` 不依赖页面，只发布契约数据。
6. 功能模块之间只通过稳定 ID、路由参数和应用服务协作，不相互导入内部状态。

## 稳定层与变化层

| 层           | 主要内容                             | 变化频率         |
| ------------ | ------------------------------------ | ---------------- |
| 契约         | 文献、段落、实体、证据、时空、发布包 | 最低，升级需迁移 |
| 领域内核     | 证据规则、文本规则、仓储端口、用例   | 低               |
| 适配器       | 静态包、搜索引擎、数据库、API        | 中               |
| 功能模块     | 书库、阅读、地图、人物、文博、检索   | 中高             |
| 数据管线插件 | 不同来源的导入与处理器               | 高               |

## 一条功能如何穿过系统

以“地图点击人物并回到原文”为例：地图模块得到 `MapObservation.entityId` → 人物模块调用 `knowledge.openEntity` → 返回带 `passageIds` 与 `Assertion.evidence` 的档案 → 阅读器使用 `PassageId` 打开原文。整个链路没有复制人物、地点或出处模型。

## 不可破坏的规则

- 原文不可被简繁转换、译文或人工润色覆盖。
- 每条正式知识主张至少有一处证据。
- 跨模块引用只能使用类型化 ID。
- 页面不得拥有持久化业务真相；状态只是查询和展示状态。
- 新数据源必须在管线入口适配，新存储必须在仓储端口后适配。
- 契约破坏性变更必须升级版本，并提供发布包迁移方案。

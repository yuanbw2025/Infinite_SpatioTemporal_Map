# 项目治理与交付机制

世界级开源项目不能只依赖某一个开发者的记忆。本文件把产品、架构、领域、质量和发布职责转化为可审查流程。

## 1. 决策视角

每项重要变更必须同时回答：

| 视角        | 必答问题                                           |
| ----------- | -------------------------------------------------- |
| 产品        | 服务哪类用户任务？成功指标是什么？明确不做什么？   |
| 地方志/史料 | 来源可靠吗？原文、异文、纪年、地名和争议如何表达？ |
| 架构        | 属于哪个事实模块或投影？依赖方向是否正确？         |
| 数据        | 从原件到发布物能否完整追溯、重建和回滚？           |
| 质量        | 哪些测试、性能、无障碍和安全门禁证明它完成？       |
| 项目管理    | 里程碑、风险、依赖、迁移和回滚方案是什么？         |
| 开源社区    | 新贡献者能否理解、运行、验证和扩展？               |

## 2. 变更等级

- L0 文档/文案：正常评审；
- L1 模块内部实现：需要测试，不改变端口；
- L2 跨模块用例或端口：需要架构影响说明；
- L3 契约、领域概念、依赖方向、发布流程：必须 ADR、迁移器和回滚方案；
- L4 数据不可逆操作、安全/权利变化：双人复核并演练恢复。

## 3. 里程碑门禁

每个里程碑按顺序通过：

1. Problem Gate：用户问题、行业价值、非目标明确；
2. Architecture Gate：模块归属、契约和 ADR 明确；
3. Data Gate：来源、权利、血缘和样本明确；
4. Quality Gate：测试矩阵、性能和安全达标；
5. Release Gate：版本、变更日志、演示和回滚可用；
6. Evidence Gate：文档中的“已实现”能由代码、测试或公开演示证明。

## 4. 工作项要求

Issue 应包含背景、用户价值、验收标准、非目标、架构影响、数据/权利影响和风险。PR 应包含变更摘要、测试证据、截图或数据样本、性能影响、迁移与回滚说明。

禁止以“先写完再补测试”“临时复制一套”“等数据来了再定义语义”作为合并理由。

## 5. 风险账本

持续维护以下最高风险：契约漂移、原文损坏、错误实体合并、历史地理误配、权利不明、不可回滚发布、静态模式规模瓶颈、依赖供应链、单人知识集中。每项风险必须有责任人、触发条件、缓解措施和验证日期。

## 6. 发布纪律

- 应用、数据和契约分别版本化；
- 正式发布从干净环境可重复构建；
- 生成校验值、来源清单、SBOM、测试与发布报告；
- 旧发布物不可修改，支持一键回滚；
- 实验功能明确标识，不能写入“已完成”清单。

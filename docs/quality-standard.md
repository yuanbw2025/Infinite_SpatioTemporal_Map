# 参赛级质量标准

本标准同时约束代码专家、产品专家、项目管理者和地方志内容团队。功能数量不能抵消质量债务。

## 1. 完成定义

一项功能只有同时满足以下条件才算完成：

- 需求与非目标清楚；
- 属于既有领域模块或有已接受 ADR；
- 不产生第二事实源；
- 类型、契约、错误和空数据行为明确；
- 单元、集成或端到端测试覆盖关键风险；
- 有可访问性、性能和安全检查；
- 文档、示例和迁移说明同步；
- CI 全绿且没有提高既有技术债务基线。

## 2. 强制质量门禁

| 类别           | 门禁                                                                     |
| -------------- | ------------------------------------------------------------------------ |
| 格式与静态分析 | Prettier、Python formatter/linter、TypeScript strict、禁止未说明的 `any` |
| 依赖           | 自动检查分层和模块依赖，禁止循环依赖                                     |
| 契约           | Schema 生成无差异；TS/Python 使用同一契约正反例                          |
| 数据权威       | 单一活动 DataContext；所有服务和派生投影来源版本一致                     |
| 测试           | domain/application/adapter/pipeline 全部有测试；关键不变量分支 100%      |
| 覆盖率         | 全仓行覆盖率 ≥ 85%，domain 与发布/审核 ≥ 95%                             |
| 数据           | 引用、字符范围、几何、时空、权利、审核与来源门禁通过                     |
| 构建           | 公众端、编辑端、管线可重复构建                                           |
| 安全           | 依赖审计、密钥扫描、最小权限、SBOM                                       |
| 文档           | README、架构、ADR、变更日志和贡献指南一致                                |

覆盖率不是质量本身；关键规则必须有边界、错误和性质测试。

当前 P0 门禁采用可持续抬升的初始线：契约运行时代码行/语句/函数 100%，核心 application/domain 行与语句 95%、函数 100%，关键 Python 发布链综合（含分支）70%。这不是终极标准的降级；阈值只能提高，待适配器、来源接入和 UI 测试纳入后，必须达到上表全仓 85% / 关键域 95% 的正式参赛线。

## 3. 测试矩阵

- Contract：每个版本提供合法/非法黄金样本，TS 与 Python 结果一致。
- Domain：证据、原文、时空、审核状态、合并和争议规则。
- Application：用例在内存端口上的行为与错误。
- Adapter contract：静态、数据库、远程适配器运行相同测试套件。
- Data authority：所有用例读取同一 `publicationId/contentChecksum`，禁止模块私有事实副本。
- Pipeline：提取、无损分段、稳定 ID、候选、审核、对齐、原子发布。
- Component：阅读器、地图控制、审核表单和错误状态。
- E2E：书目→原文→实体→地图/图谱→证据，以及数据导入→审核→发布。
- Data regression：真实小型公开样本的确定性快照。

## 4. 代码可维护性

- 函数优先保持单一职责，圈复杂度目标 ≤ 10，禁止超过 15。
- 业务文件目标 ≤ 300 行；超过 400 行必须拆分或在评审中说明。
- Vue 页面负责组装，IO/状态机进入 composable，复杂图形进入独立 renderer。
- CSS 使用 token、base、layout、component、feature 分层，禁止持续扩张单一全局文件。
- CLI 只解析参数和调度命令；业务逻辑进入可测试模块。
- 错误必须包含可行动上下文，不能吞掉数据一致性错误。

## 5. 产品与行业质量

- 所有历史名称同时保留使用时期和原始写法。
- 公元换算不能覆盖原纪年；不确定性必须显式。
- 现代行政区不能冒充历史地点身份。
- 版本异文、争议主张和不同学术意见并列呈现。
- 专家术语与公众名称可并存，但必须指向同一实体身份。
- 无权公开的数据不能因“技术可读取”而进入发布物。

## 6. 性能预算

- 非地图首屏 JS gzip 目标 ≤ 150 KB。
- 地图路由含 GIS 引擎 gzip 目标 ≤ 350 KB，独立懒加载。
- 10 万段落规模下，远程查询 p95 ≤ 500 ms；静态模式必须明确建议规模上限。
- 地图交互目标 60 FPS，最低不得长期低于 30 FPS。
- 发布管线同输入产生确定性输出，支持增量与缓存，不以牺牲审计为代价。

## 7. 可访问性与国际化

- 公众端目标 WCAG 2.2 AA。
- 键盘可完成导航、地图替代列表、阅读和审核核心操作。
- 色彩不能是审核状态的唯一表达。
- UI 文案与史料内容分离，中文史料不被 locale 转换。

## 8. 安全与供应链

- 仓库禁止提交令牌、私钥和受限原件。
- 外部 URL、上传 JSON、影印清单和富文本按不可信输入处理。
- CI 生成依赖锁、许可证清单和 SBOM；高危依赖阻止发布。
- 编辑端未来联网时采用最小权限、审计日志和不可抵赖决策记录。

## 9. 开源项目治理

正式公开前必须具备：

- 中英文 README 与架构概览；
- LICENSE、第三方声明、数据权利说明；
- CONTRIBUTING、CODE_OF_CONDUCT、SECURITY、发布与支持政策；
- Issue/PR 模板、语义化版本、变更日志；
- 一键开发环境、公开样本和可复现演示；
- 路线图明确“已实现、实验性、计划中”，不得夸大完成度。

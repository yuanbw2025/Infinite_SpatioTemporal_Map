# 扩展指南

## 增加一种新数据

1. 判断它是实体、带证据的主张，还是文献结构。
2. 优先使用现有 `Entity + Assertion + EvidenceSpan` 表达。
3. 只有普遍、稳定且无法由主张表达的信息才进入核心契约。
4. 先修改唯一 JSON Schema 源，生成 TypeScript DTO，并更新契约版本、迁移器和正反例。
5. 在数据管线增加来源适配器或处理阶段，并输出统一发布包。

## 增加一个公众功能

1. 判断它是事实模块还是查询投影，复用现有用例；缺少用例时先在 application 添加用例，在 ports 添加最小端口。
2. 在 `apps/web/src/features` 新建独立目录。
3. 使用 `defineFeature` 声明路由、导航、能力和依赖。
4. 在功能注册表接入；不得另建全局状态、HTTP 客户端或数据模型。

## 更换存储

实现目标能力端口并运行统一适配器合规测试，只在组合根替换实现。功能模块和领域内核不改；禁止复制时间线、研究判断等应用规则。

## 架构评审问题

- 这项改动是否创造了第二个实体、地点、时间或出处模型？
- 页面是否绕过应用服务直接读写数据？
- 机器生成内容是否可能覆盖原文？
- 用户能否从结论返回具体段落？
- 新功能能否作为模块注册，而无需复制基础设施？
- 这是领域事实、查询投影，还是只属于界面的临时状态？
- 规则是否错误地进入了 adapter 或页面？
- 是否有测试能在未来替换存储后证明语义不变？
